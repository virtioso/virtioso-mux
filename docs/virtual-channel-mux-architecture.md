# Virtual Channel Mux (VCMux) Architecture

*Current as of 2026-05-13. Covers the wire protocol, both sender implementations
(CAmkES ConsoleMux and virtioso-muxd), the host-side vcmuxer tool, and the
physical transport layer.*

---

## What it is

VCMux (Virtual Channel Mux) is a byte-stream multiplexer protocol: multiple
logical channels share one physical transport stream using escape-byte framing.
The physical transport is pluggable — currently UART, with TCP and SSH as future
options.

The protocol originated from NVIDIA's Tegra Combined UART (TCU) mux conventions
but is independent of TCU hardware. The 0xfe escape byte was deliberately chosen
to differ from NVIDIA's 0xff outer escape so VCMux streams can be carried
transparently inside a real NVIDIA TCU stream without collision.

---

## Prior art: 3GPP TS 27.010 (GSM 07.10 / CMUX)

The closest published analogue is **3GPP TS 27.010** (GSM 07.10), the standard
multiplexer protocol for GSM modems. CMUX multiplexes multiple virtual serial
channels (DLC frames) over one physical serial line using a 0xF9 flag byte and
HDLC-style framing.

VCMux uses the same conceptual model — multiple logical channels over one byte
stream — but with a simpler two-byte escape scheme:

| Feature | 3GPP CMUX | VCMux |
|---|---|---|
| Frame marker | 0xF9 (HDLC flag) | 0xfe (ESC byte) |
| Channel ID | DLCI field in header | Stream ID byte after ESC |
| Frame format | HDLC: flag/addr/ctrl/len/data/FCS/flag | `[0xfe][id][data...][0xfe][0x00]` |
| Control records | UIH frames on DLCI 0 | `[0xfe][0xfd][type][len_hi][len_lo][payload]` |
| Flow control | RTS/CTS per DLC | None (backpressure is a known gap) |
| Nesting | Not designed for it | Transparent (outer sees opaque bytes) |

CMUX is more complete but requires an HDLC parser and CRC computation. VCMux
trades features for simplicity: the entire parser is a two-state machine.

## Wire Protocol

### Escape scheme

The ESC byte is `0xfe`. Every framing sequence begins with `0xfe`. A literal
`0xfe` byte in payload data is escaped as `0xfe 0xfe`.

Valid stream IDs: `0x01`–`0xfc`. IDs `0x00`, `0xfd`, and `0xfe` are reserved:

| Byte after 0xfe | Meaning |
|---|---|
| `0x01`–`0xfc` | Switch active channel to this stream ID |
| `0x00` | Clear active channel → return to unframed/default output |
| `0xfd` | Control record follows |
| `0xfe` | Literal `0xfe` in payload (escape) |

### Data frame format

```
[0xfe] [stream_id]  ← open frame for stream_id
[data bytes]        ← payload; each 0xfe in data is escaped as 0xfe 0xfe
[0xfe] [0x00]       ← close frame, return to default stream
```

Stream selection is sticky: once a channel is selected with `[0xfe][stream_id]`,
subsequent bytes belong to that channel until another `[0xfe][stream_id]` or
`[0xfe][0x00]` is sent.

### Control frame format

```
[0xfe] [0xfd] [ctrl_type: u8] [len_hi: u8] [len_lo: u8] [payload: len bytes]
```

Control types:

| Type | Hex | Sender | Payload |
|---|---|---|---|
| `CTRL_CONNECTED` | `0x01` | virtioso-muxd | `[stream_id: u8][name bytes...]` |
| `STREAM_REGISTRY` | `0x02` | ConsoleMux | JSON stream manifest |
| `DOWNLINK_ACK` | `0x03` | ConsoleMux | empty |
| `CTRL_DISCONNECTED` | `0x04` | virtioso-muxd | `[stream_id: u8]` |

## CAmkES Side: ConsoleMux Component

**Source:** `components/ConsoleMux/src/console_mux.c`

ConsoleMux is a CAmkES component that acts as the multiplexer for seL4 component
console streams. It provides:

- **Uplink** (`mux_batch` RPC interface): components call this to send console
  output. ConsoleMux frames each payload with 0xfe framing and writes it to UART.
- **Downlink** (`GetChar` interfaces): ConsoleMux demuxes incoming UART bytes and
  delivers them to the correct component via seL4 notifications.

### Stream registry (static, CAmkES build time)

At boot, ConsoleMux emits a `STREAM_REGISTRY` control frame containing the
complete JSON stream manifest generated by
`tools/generate_camkes_stream_registry.py`. This manifest lists every component
stream with its ID, name, and direction. The host-side vcmuxer reads this manifest
and creates one PTY per stream.

The stream IDs are compile-time constants (`console_stream_ids.h`) — the layout
is fully deterministic and identical across runs.

## Target-Side Daemon: virtioso-muxd

**Source:** `sources/virtioso-muxd/`

virtioso-muxd is a Rust daemon that runs inside a Linux VM (or bare Linux
deployment). It provides dynamic channel enrollment via a Unix socket:

1. A process (`virtioso-mux-exec`) connects to the socket and sends
   `[name_len: u8][name bytes...]`.
2. virtioso-muxd allocates a stream ID from the pool (`0x01`–`0xfc`), replies
   with the ID, and emits a `CTRL_CONNECTED` control frame on the mux transport.
3. All data the process writes is forwarded as a VCMux data frame for that stream ID.
4. On disconnect, a `CTRL_DISCONNECTED` frame is emitted.

Unlike ConsoleMux, channel enrollment is runtime-dynamic — IDs are not fixed at
build time. See the backlog item on static channel manifests for Linux parity.

## Host Side: vcmuxer Tool

**Source:** `sources/tcu_muxer/` (binary: `vcmuxer`)

vcmuxer is a C daemon that demuxes the VCMux byte stream arriving from the target
and creates a PTY per channel on the host. It supports two outer modes:

| Flag | Outer mode |
|---|---|
| `-O raw` | Input is already a raw VCMux 0xfe stream |
| `-O nvidia-tcu` | Input is wrapped in NVIDIA TCU 0xff framing; `-C <tag>` selects the client carrying VCMux traffic (default: `CCPLEX`) |

With `-A`, vcmuxer enters runtime-introspection mode: it waits for a
`STREAM_REGISTRY` or `CTRL_CONNECTED` control frame and creates PTYs dynamically.

### Built-in channels (always present in `-A` mode)

| PTY name | Purpose |
|---|---|
| `raw_ccplex` | Pre-registry and unframed CCPLEX payload |
| `autopilot_control` | Bidirectional Autopilot control channel |
| `physical_uart_default` | Unframed bytes when no channel is selected |

Each PTY creation is reported to stdout as a JSON `session_open` record for
Autopilot integration:

```json
{"event":"session_open","name":"vm1_guest_console_sink","kind":"camkes_component_stream","stream_id":2,"pty_path":"/dev/pts/19","log_path":"..."}
```

## Physical Transport

Current: Orin AGX UARTI hardware → `/dev/ttyAMA0` inside isengard →
`/dev/ttyACM1` USB-serial on the Autopilot host → vcmuxer.

```
isengard (seL4)
  ConsoleMux component
    → UARTI /dev/ttyAMA0
      → /dev/ttyACM1 (host USB-serial)
        → vcmuxer -A -O nvidia-tcu -d /dev/ttyACM1
            ├── PTY: raw_ccplex
            ├── PTY: autopilot_control
            ├── PTY: physical_uart_default
            └── PTY: vm0_guest_console_sink, vm1_guest_console_sink, ...
```

For the Linux deployment (inside a VM), virtioso-muxd replaces ConsoleMux:

```
Linux VM
  virtioso-mux-exec (wraps a process)
    → Unix socket → virtioso-muxd
        → UART sink / TCP sink → (same vcmuxer path on host)
```

### Coexistence and nested muxing

ConsoleMux and virtioso-muxd can coexist on the same physical UART. If a Linux
guest VM runs virtioso-muxd, its output appears as a single opaque VCMux stream
to the outer ConsoleMux. The outer STREAM_REGISTRY describes the VM's channel as
one stream; the inner VCMux traffic within that channel is demuxed by a second
vcmuxer instance on the host side, connected to the PTY produced by the first.

No architecture changes are needed — nesting is transparent because VCMux frames
are self-delimiting and carry arbitrary byte payloads.

## Known Gaps (Backlog)

| Gap | Description |
|---|---|
| No uplink flow control | A noisy channel can starve others at UART rate |
| No version negotiation | Protocol extensions are flag days |
| STREAM_REGISTRY loss | No Autopilot timeout/fallback if registry never arrives |
| vcmuxer no UART reconnect | USB-serial drop kills the daemon with no recovery |
| STREAM_REGISTRY length cap | JSON payload silently capped at 65535 bytes |

See the VCMux section of the Virtioso plan doc for detailed mitigations.
